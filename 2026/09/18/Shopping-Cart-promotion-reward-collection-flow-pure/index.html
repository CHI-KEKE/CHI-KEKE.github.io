全貌鏈路

同樣是修改回饋給券活動的商品，從後台畫面圈選與從批次匯入進入，會走到不同的 API。畫面圈選直接修改原商品集合；批次異動會先比較商品清單，再更新活動引用的集合。

這裡的商品集合是 collection，由 collectionId 識別。以下聚焦 RewardReachPriceWithCoupon 已有指定／排除商品集合的流程；實際執行仍需通過 API 驗證。

草地綠為處理步驟，棕色菱形為判斷，奶白色為結果；配色用於區分類型，不代表風險程度。圖中只展開給券活動的既有 fixed 商品集合，以及切換成全站或取消排除範圍的分支。

CollectionService 直接增刪原集合，並建立 SyncCollectionToPromotionTagJob。這條路徑不經過活動的 UpdateAsync。

salepage-update 會比較異動前後的商品清單。有實際新增或移除才進入 UpdateAsync；重複新增已有商品、移除不存在的商品，都不會在這個差異分支重建集合。

活動儲存也能直接進入更新流程。 POST /api/promotion-rules/update 直接呼叫 UpdateAsync，沒有經過上述商品差異判斷。給券活動處理既有 fixed collection 時，即使商品清單相同，也會進入重建分支。salepage-update 呼叫 UpdateAsync 則是內部方法呼叫，不會再發送一次 HTTP update 請求。

範圍由「全站排除商品」改成「全站活動」時，排除類型從 SalePage 變為 None，會刪除目前排除範圍引用的集合。這與一般商品異動重建後保留舊集合，是不同分支。

純全站且尚無排除集合時，salepage-update 的新增操作會先建立排除範圍，再進入商品比較；這個前置情境不包含在上圖的既有集合主線中。

歷史保留：規則與商品範圍

訂單成立後，活動商品可能已經異動，回饋卻還沒開始計算。此時除了找回下單當時的活動規則，也要考慮規則引用的商品集合，是否仍保有當時的內容。

一筆延後計算的訂單

以下是假設案例，用來說明回饋計算時間與下單時間不同時，歷史資料的用途。活動原本適用商品甲、乙，後來移除商品甲；這次異動走重建既有 fixed collection 的流程，且更新成功。

  1. 10:00 建立活動版本 V1。 V1 引用舊集合，包含商品甲、乙。
  2. 10:30 消費者購買商品甲。 這筆訂單對應下單當時的 V1。
  3. 11:00 活動移除商品甲，建立版本 V2。 V2 引用新集合，只包含商品乙；本次重建未刪除舊集合。
  4. 12:00 Worker 開始計算這筆訂單的回饋。 使用 10:30 的訂單時間查詢規則，選回 V1。

這裡只討論商品範圍的歷史保留。商品甲是否最終獲得回饋，仍需由該版本的完整活動條件與計算結果決定。

歷史規則依訂單時間選取

以訂單的 10:30 為查詢時間，先篩選符合時間條件的紀錄，再取最近一次活動更新。

展開規則查詢方法與快照欄位

給券 Worker 使用 OrderDateTime 呼叫 GetAndCheckPromotionRuleAsync，再經 GetPromotionRuleRecordAsync 查詢歷史規則。

WebAPI 先篩選 PromotionEngineDateTime <= OrderDateTime 的紀錄，再取活動更新時間最大的一筆，讀取其 S3 快照。因此案例中的查詢時間是 10:30，會選取 10:00 的 V1，而不是 11:00 的 V2。這個選取方式也不是直接取最大的 Version。

取得規則後，Worker 將該版本的 RuleJson 放入計算請求，並將 CalculateDateTime 設為 OrderDateTime。規則快照封裝包含 Rule、PromotionEngineDateTime、IncludeCollectionIds 與 ExcludeCollectionIds 等資料；其中的集合 ID，將歷史規則連到對應的商品範圍。

展開重建方法與原地修改的推導前提

ReCreateCollectionAndUpdateRelationAsync 建立新集合、填入更新後的商品全集，再更新活動關聯。新 ID 會寫入活動規則，更新流程也會保存新的 RuleRecord 與 S3 快照；重建方法本身沒有刪除舊集合。

如果反過來沿用舊 ID，直接把舊集合中的商品甲移除，舊規則即使仍被保存，引用的集合內容也已經改變。在計算端透過該 ID 讀取商品資格、且沒有其他歷史快照機制介入的前提下，選回 V1 仍可能取得異動後的商品範圍。

保存規則 JSON，不等於保存它引用的所有資料。 重建並保留舊集合，可以避免本次更新覆蓋舊規則引用的商品範圍。但這不表示集合天生不可修改，也不表示其他流程永遠不會刪除它。

三種識別與版本，各自保存什麼

資料 代表的意義 歷史保留的判讀界線
RuleRecord.Version 活動規則歷程的遞增版本編號。 目前查詢依活動更新時間選取紀錄，不是直接選最大版本號。
CollectionId 一份商品集合的識別碼。 規則保存 ID，不代表該 ID 對應的商品內容不可修改。
UpdateIdx 同一個集合的內容異動版本。 目前分析尚不能證明計算端會使用它取得歷史商品內容。

因此，若要改成所有版本都沿用同一個集合，還需要可保存、可讀取歷史商品範圍的機制，例如依 CollectionId + 版本 查詢，或保存完整商品快照。這些是可評估的設計方式，不是本次已確認的現行能力。

已確認的保留行為與待查事項

依分析文件，已確認 Worker 會依訂單時間選取歷史規則，也已確認給券活動的重建方法保留舊集合。兩者支持「重建用來隔離不同活動版本的商品範圍」這個設計目的推論；原始 Story 的需求說明尚未核對。

情境 已確認行為 還需要查核
SMS 原地修改集合 不會進入活動整體更新與重新產生 RuleRecord 的流程。 如果舊規則引用同一個 ID，計算端是否另有商品快照或版本查詢保護？
範圍切換時刪除集合 目前範圍引用的集合會被呼叫刪除，歷史規則仍可能引用它。 下游刪除語意與計算端的讀取方式，會如何影響歷史資料？
商品相同仍重建 活動更新進入既有 fixed collection 的重建分支時，不比較商品是否相同。 歷史保留需求本身不足以證明每次都必須換 ID。是否能共用集合，仍需確認關聯、版本及其他副作用。

尚不能據此判定已發生錯算。 本次來源尚未追到底層計算服務如何取得集合中的商品資格，也未確認 Collection Service 的刪除策略、保存期限與清理機制。「本次重建保留舊集合」是已確認行為；「所有歷史商品範圍都能永久還原」則尚無足夠證據。

SMS 商品圈選：直接修改原 Collection

03 ／ SMS 商品圈選
同一份集合，更新裡面的商品
後台圈選商品時，畫面會帶著既有的集合 ID，把這次選取的商品送往後端。新增完成後，活動仍引用原本的集合，改變的是集合裡的商品內容。

展開完整 API 路徑與內部責任

  • SMS 前端 Service 呼叫 Api/PromotionEngine/EditTargetIdList，進入 SMS PromotionEngineController.EditTargetIdList 與同名 Service 方法。
  • SMS PromotionEngineService.EditTargetIdList 驗證登入及活動，組成 CollectionUpdateRequestEntity。
  • SMS Nine1PromotionWebApiHttpClient.UpdateCollectionSalepages 發送 POST /api/salepage-collections/update。
  • Promotion WebAPI CollectionController.Update 依 IsRemoved 交給 CollectionService 的新增或移除方法。
  • CollectionHttpClientWithAudit 使用原 CollectionId 呼叫下游，異動商品並處理稽核。
  • CollectionService 建立 SyncCollectionToPromotionTagJob。時序圖中的自我呼叫是內部責任摘要，不表示同步任務已執行完成。
  • SMS 再取得商品數量，將處理結果與 TotalCount 回傳前端。

請求欄位：商品與操作方向如何傳遞

畫面傳入的是「這次要異動的商品」，後端將欄位轉成 WebAPI 的請求格式，並沿用既有集合 ID。

SMS 請求 WebAPI 請求 這條鏈路中的用途
IsRemove IsRemoved false 是新增，true 是移除；本章已定位的 UI 回呼傳入 false。
RequestIds SalePageIdList 本次要新增或移除的商品 ID 清單。
既有集合 ID CollectionId 指定要修改哪一份商品集合。

商店資料 ShopId 指定此次操作的商店。

上下兩個方框是同一份集合在不同時間的內容，不是兩個不同的 collection。箭頭表示本次新增操作，collectionId 沒有更換。

這條路徑不呼叫活動的 UpdateAsync，也沒有改走「重建 collection、重新產生活動 RuleRecord」的流程。稽核紀錄與 PromotionTag 同步任務，都不能視為活動整體更新。

第二章的歷史保留問題也因此成立：若舊規則引用同一個集合 ID，就需要進一步確認計算端如何讀取歷史商品範圍；僅憑本章鏈路，尚不能判定已造成錯算。

其他商品類型、補充欄位與查核邊界

  • SMS TargetType = Category 改走動態 collection；TargetType = MustSalePage 改走必購商品處理，均不屬於本章一般 fixed 商品集合主線。
  • WebAPI 的 IsRemoved = true 從原集合移除商品，false 在原集合新增商品，兩者皆沿用集合 ID。
  • TargetType、IsNeedRecordIo、UpdatedUser 等欄位供歷程處理；collection 的 UpdateIdx 是同一集合的異動版本，不等於更換 CollectionId。
  • 活動規則可保存帶前綴的集合識別值，呼叫下游前通常透過 GetCollectionIdWithoutPrefix() 去掉前綴，不能只按字串外觀判定是否換了集合。
  • API 驗證失敗時不進入後續核心更新。分析文件另指出，SMS Service 會將 collection 修改 API 的 400／500 回應轉成後台對應例外與訊息；本章時序圖未展開這些例外分支。

批次商品異動：從匯入任務到 Collection 重建

04 ／ 批次商品異動
先比對商品，再更新活動引用的集合
商品清單從後台匯入後，交由批次任務處理。既有集合的商品確實有增減時，才進入活動更新，建立新集合並讓活動改用新的商品範圍。

任務交接：從 SMS 匯入到 SCM NMQ

SMS 回饋活動商品匯入先建立批次任務，SCM NMQ 再解析資料並執行商品異動。任務建立與後續處理，是兩個不同階段。

前端批次類型與 NMQ 處理服務

SMS 畫面 pages/BatchUpLoad/SalePage/index.tsx 選擇 ModifyRewardPromotionSalePage。共用流程 AbstractCreateBatchTaskBaseService.CreateBatchTask 會呼叫 CreateBatchUploadNMQTask。

但 SMS 的 BatchModifyPromotionSalePageService.GetBatchUploadType() 回傳 BatchModifyPromotionSalePage，匯入解析另支援 ModifyRewardPromotionSalePage。不能只看畫面選項，就推定最終 NMQ 任務類型字串。

BatchModifyPromotionSalePage BatchModifyPromotionSalePageService
ModifyRewardPromotionSalePage BatchModifyPromotionSalePageService

兩種類型在 BatchUploadTaskProcessSetting 都註冊到同一個處理服務，後續由 DoProcess 解析批次資料。

跨服務呼叫：SCMAPIV2 是 WebAPI 的直接呼叫端

SCM NMQ 組成商店、活動與商品增刪資料，透過 SCM API Client 呼叫 SCMAPIV2，再由 SCMAPIV2 轉送 Promotion WebAPI。

完整 API、請求欄位與轉送條件

  • SCM NMQ 使用 Client Factory 建立 IPromotionClient，組成 ShopId、活動 Id、ModifyType 與 SalePageIds，呼叫 promotionClient.ModifyPromotionSalePages(request)。
  • SCM API Client 發送 POST /v2/Promotion/ModifyPromotionSalePages，進入 SCMAPIV2 PromotionController.ModifyPromotionSalePages 與 PromotionService.ModifyPromotionSalePages。
  • 符合條件時，SCMAPIV2 經 ModifyPromotionSalePagesWithPromotionApi，呼叫 Nine1PromotionWebApiHttpClient.UpdateSalepageScopes，發送 POST /api/promotion-rules/salepage-update。
SCMAPIV2 判斷條件 處理去向
MongoDB 活動 ID。 轉送 Promotion WebAPI。
非 MongoDB 活動，類型位於 Nine1PromotionSwitchType，且 IsEnableSwitchToCollectionUI 為 true。 轉送 Promotion WebAPI。
其餘情況。 留在 SCMAPIV2 原有處理流程。

依分析文件，給券類型位於 Nine1PromotionSwitchType，且 IsEnableSwitchToCollectionUI 對給券直接回傳 true，因此符合轉送條件。WebAPI 的 Controller 經 V2 Service 入口後，非 MongoDB 活動委派到 PromotionEngineService.ModifyPromotionSalePages；本章後續的規則比較與重建位於此服務。

差異判斷：商品真的有增減才進入更新

WebAPI 先找到活動適用或排除範圍的集合，讀取既有商品全集，再套用本次 Add 或 Remove。給券走支援 RuleRecord 的比較分支。

既有集合的判斷 ／ 重複新增與無效移除都不重建

箭頭表示服務內的商品比較流程。新增已有商品時，聯集數量不變；移除不存在的商品時，實際移除筆數為 0。本圖限定已存在商品／排除範圍的一般流程。

純全站、尚無排除集合時，會先做一次前置更新。 原活動為 Shop + None，收到 Add 時，方法先將排除範圍改為 SalePage 並呼叫一次 UpdateAsync，建立可操作的排除範圍，再讀取及比較商品。因此「沒有差異就完全不更新」不能直接套用此情境。

如何找出集合，以及交給更新流程的資料

  • 先讀取活動詳細資料，轉成完整活動更新 Entity。
  • 從 IncludedProductScopes 或 ExcludedProductScopes 找出集合。有傳 Tag 時比對指定範圍；未傳且存在可用集合時取第一筆。Tag 是此 WebAPI 的選用欄位，不表示上述 NMQ 請求一定有傳入。
  • 給券位於 _ruleRecordSupportedPromotionTypes，因此走比較商品清單、更新活動的分支。
  • 確認有異動後，保留既有料號資料，將異動後的商品全集填入 IncludeTargetIdList 或 ExcludeTargetIdList，再交給內部 UpdateAsync。

UpdateAsync 處理給券的既有 fixed collection 時，建立新集合、填入商品全集，再更新活動關聯與規則，保存 RuleRecord／S3 快照。本次重建不刪除舊集合，與第三章直接修改原集合的結果不同。

比較在前，重建在後。 salepage-update 在這條既有集合主線先判斷商品差異，才內部呼叫 UpdateAsync，不會再送一個 HTTP 請求到活動 update API。直接呼叫 POST /api/promotion-rules/update 則不經過這個差異判斷，因此商品相同也可能進入重建。

失敗處理與查核邊界

  • API 驗證失敗時，不進入後續核心更新；主線不代表所有活動狀態都允許商品異動。
  • 給券異動遇到不支援的適用／排除組合，ModifyPromotionSalePages 會拋出 NotSupportedException。
  • SCM NMQ 收到 SCM API 非 Success 結果時，記錄 API 錯誤並進入批次失敗訊息處理。
  • 文件未確認跨資料庫、Collection HTTP 呼叫與 NMQ 任務的完整失敗補償；不能由呼叫端 TransactionScope 推定所有外部服務都能原子回滾，也不補造重試次數或補償順序。
  • 歷史訂單能否完整還原商品資格，仍需核對底層計算服務的集合讀取方式，不能只憑「本次保留舊集合」就推定所有歷史內容都安全。

補充風險：範圍切換刪除集合，舊訂單還能取得商品範圍嗎？

一般批次商品增刪的重建流程會保留舊集合。但活動更新若將原本的 SalePage 範圍改成 Shop／None，且該範圍原本有集合，請求通過驗證後，會對目前引用的集合呼叫刪除 API。Shop 通常對應全站適用範圍，None 對應取消排除範圍，需分別看更新的是哪一側。

實線是此情境的事件先後，並非同一支程式的連續呼叫；虛線是待驗證的風險推論。呼叫 DELETE 已有靜態分析依據，集合是否不可讀及計算是否受影響，仍未確認。

這是尚待驗證的歷史引用風險，不能直接判定已經錯算。 已確認程式會呼叫 DELETE，但 Collection Service 採實體刪除或邏輯刪除、刪除後能否歷史查詢，以及計算端查無集合時會報錯、視為空集合或採取其他處理，均尚未確認。

刪除目標是該範圍目前引用的集合，不會在此分支遍歷清除歷次重建留下的所有集合。另外，給券批次移除最後一筆排除商品，不會在其 RuleRecord 分支自動將 ExcludeTargetType 改為 None；商品清單變空與明確切換範圍類型，應分開判讀。
