回饋給券活動商品異動的全貌鏈路

Created2026-09-18|Updated2026-09-25|Shopping-Cart
|Post Views:

全貌鏈路

同樣是修改回饋給券活動的商品，從後台畫面圈選與從批次匯入進入，會走到不同的 API。畫面圈選直接修改原商品集合；批次異動會先比較商品清單，再更新活動引用的集合。

這裡的商品集合是 collection，由 collectionId 識別。以下聚焦 RewardReachPriceWithCoupon 已有指定／排除商品集合的流程；實際執行仍需通過 API 驗證。

呼叫來源：SMS 畫面與 SCM NMQ 批次

呼叫端接收端與方法完整 API 路徑
SMS 前端SMS EditTargetIdListApi/PromotionEngine/EditTargetIdList
SMS 後端Promotion WebAPI，POST/api/salepage-collections/update
SCM API ClientSCMAPIV2，POST/v2/Promotion/ModifyPromotionSalePages
SCMAPIV2Promotion WebAPI，POST/api/promotion-rules/salepage-update

SCM NMQ 由 BatchModifyPromotionSalePageService.DoProcess 呼叫 Client 的 ModifyPromotionSalePages。給券活動符合 SCMAPIV2 的轉送條件，因此進入 salepage-update。

處理分支：原集合增刪、重建與刪除

CollectionService 直接增刪原集合，並建立 SyncCollectionToPromotionTagJob。這條路徑不經過活動的 UpdateAsync。

salepage-update 會比較異動前後的商品清單。有實際新增或移除才進入 UpdateAsync；重複新增已有商品、移除不存在的商品，都不會在這個差異分支重建集合。

活動儲存也能直接進入更新流程。 POST /api/promotion-rules/update 直接呼叫 UpdateAsync，沒有經過上述商品差異判斷。給券活動處理既有 fixed collection 時，即使商品清單相同，也會進入重建分支。salepage-update 呼叫 UpdateAsync 則是內部方法呼叫，不會再發送一次 HTTP update 請求。

範圍由「全站排除商品」改成「全站活動」時，排除類型從 SalePage 變為 None，會刪除目前排除範圍引用的集合。這與一般商品異動重建後保留舊集合，是不同分支。

純全站且尚無排除集合時，salepage-update 的新增操作會先建立排除範圍，再進入商品比較；這個前置情境不包含在上圖的既有集合主線中。

鏈路來源對照
  • SMS：rewardCoupon.config.tsx:187 的 onUpdate → PromotionEngineService.EditTargetIdList:3641 → Nine1PromotionWebApiHttpClient.UpdateCollectionSalepages:166。
  • SCM NMQ：BatchModifyPromotionSalePageService.cs:182 → SCM Client PromotionClient.cs:65。
  • SCMAPIV2：PromotionService.ModifyPromotionSalePages:788 → Nine1PromotionWebApiHttpClient.UpdateSalepageScopes:238。
  • Promotion WebAPI：CollectionService.cs:76 處理原集合；PromotionEngineService.cs:421 比較商品，:2819 分流範圍，:3049 重建集合。

來源為 2026-09-16 的「回饋給券活動商品異動與 Collection 生命週期鏈路分析」。以上為本機程式碼所確認的呼叫鏈，未比對線上部署版本。

歷史保留：規則與商品範圍

訂單成立後，活動商品可能已經異動，回饋卻還沒開始計算。此時除了找回下單當時的活動規則，也要考慮規則引用的商品集合，是否仍保有當時的內容。

一筆延後計算的訂單

以下是假設案例，用來說明回饋計算時間與下單時間不同時，歷史資料的用途。活動原本適用商品甲、乙，後來移除商品甲；這次異動走重建既有 fixed collection 的流程，且更新成功。

  1. 10:00建立活動版本 V1。V1 引用舊集合，包含商品甲、乙。
  2. 10:30消費者購買商品甲。這筆訂單對應下單當時的 V1。
  3. 11:00活動移除商品甲，建立版本 V2。V2 引用新集合，只包含商品乙；本次重建未刪除舊集合。
  4. 12:00Worker 開始計算這筆訂單的回饋。使用 10:30 的訂單時間查詢規則，選回 V1。

這裡只討論商品範圍的歷史保留。商品甲是否最終獲得回饋，仍需由該版本的完整活動條件與計算結果決定。

歷史規則依訂單時間選取

以訂單的 10:30 為查詢時間，先篩選符合時間條件的紀錄，再取最近一次活動更新。

展開規則查詢方法與快照欄位

給券 Worker 使用 OrderDateTime 呼叫 GetAndCheckPromotionRuleAsync，再經 GetPromotionRuleRecordAsync 查詢歷史規則。

WebAPI 先篩選 PromotionEngineDateTime <= OrderDateTime 的紀錄，再取活動更新時間最大的一筆，讀取其 S3 快照。因此案例中的查詢時間是 10:30，會選取 10:00 的 V1，而不是 11:00 的 V2。這個選取方式也不是直接取最大的 Version。

取得規則後，Worker 將該版本的 RuleJson 放入計算請求，並將 CalculateDateTime 設為 OrderDateTime。規則快照封裝包含 Rule、PromotionEngineDateTime、IncludeCollectionIds 與 ExcludeCollectionIds 等資料；其中的集合 ID，將歷史規則連到對應的商品範圍。

重建集合，隔離本次商品異動

兩種做法都能得到「目前只剩商品乙」的清單，差別在於舊規則引用的集合是否跟著改變。

展開重建方法與原地修改的推導前提

ReCreateCollectionAndUpdateRelationAsync 建立新集合、填入更新後的商品全集，再更新活動關聯。新 ID 會寫入活動規則，更新流程也會保存新的 RuleRecord 與 S3 快照；重建方法本身沒有刪除舊集合。

如果反過來沿用舊 ID，直接把舊集合中的商品甲移除，舊規則即使仍被保存，引用的集合內容也已經改變。在計算端透過該 ID 讀取商品資格、且沒有其他歷史快照機制介入的前提下，選回 V1 仍可能取得異動後的商品範圍。

保存規則 JSON，不等於保存它引用的所有資料。 重建並保留舊集合，可以避免本次更新覆蓋舊規則引用的商品範圍。但這不表示集合天生不可修改，也不表示其他流程永遠不會刪除它。

三種識別與版本，各自保存什麼

資料代表的意義歷史保留的判讀界線
RuleRecord.Version活動規則歷程的遞增版本編號。目前查詢依活動更新時間選取紀錄，不是直接選最大版本號。
CollectionId一份商品集合的識別碼。規則保存 ID，不代表該 ID 對應的商品內容不可修改。
UpdateIdx同一個集合的內容異動版本。目前分析尚不能證明計算端會使用它取得歷史商品內容。

因此，若要改成所有版本都沿用同一個集合，還需要可保存、可讀取歷史商品範圍的機制，例如依 CollectionId + 版本 查詢，或保存完整商品快照。這些是可評估的設計方式，不是本次已確認的現行能力。

已確認的保留行為與待查事項

依分析文件，已確認 Worker 會依訂單時間選取歷史規則，也已確認給券活動的重建方法保留舊集合。兩者支持「重建用來隔離不同活動版本的商品範圍」這個設計目的推論；原始 Story 的需求說明尚未核對。

情境已確認行為還需要查核
SMS 原地修改集合不會進入活動整體更新與重新產生 RuleRecord 的流程。如果舊規則引用同一個 ID，計算端是否另有商品快照或版本查詢保護？
範圍切換時刪除集合目前範圍引用的集合會被呼叫刪除，歷史規則仍可能引用它。下游刪除語意與計算端的讀取方式，會如何影響歷史資料？
商品相同仍重建活動更新進入既有 fixed collection 的重建分支時，不比較商品是否相同。歷史保留需求本身不足以證明每次都必須換 ID。是否能共用集合，仍需確認關聯、版本及其他副作用。
尚不能據此判定已發生錯算。 本次來源尚未追到底層計算服務如何取得集合中的商品資格，也未確認 Collection Service 的刪除策略、保存期限與清理機制。「本次重建保留舊集合」是已確認行為；「所有歷史商品範圍都能永久還原」則尚無足夠證據。
歷史保留的來源與提交紀錄
  • 規則封裝：WebAPI PromotionEngineService.cs:872，包含規則、活動更新時間與適用／排除集合 ID。
  • 版本寫入：WebAPI PromotionEngineRuleRecordService.cs:57，上傳 S3 並新增帶版本及更新時間的 RuleRecord。
  • 訂單時間：Worker PromotionRewardCouponJob.cs:273，使用 OrderDateTime 取得規則；PromotionRewardCalculateServiceBase.cs:456 傳入歷史規則查詢。
  • 版本選取：WebAPI PromotionEngineService.cs:4297，篩選不晚於查詢時間的紀錄，取最近一次活動更新並讀取 S3 快照。
  • 計算請求：Worker PromotionRewardCalculateServiceBase.cs:330，使用歷史 RuleJson，並將計算時間設為訂單時間。
  • 集合重建：WebAPI PromotionEngineService.cs:3049，建立新集合並更新關聯，方法本身沒有刪除舊集合。
  • 提交 337b3dbb：VSTS372853 - 新版給點活動異動Collection 將會新增而非覆蓋，同次加入集合重建及活動更新時寫入 RuleRecord／S3。
  • 提交 e7929ea7：VSTS484767 - 更新活動_滿額贈券支援重建collectionId，將給券加入 fixed collection 重建支援清單。

來源為 2026-09-16 的「回饋給券活動商品異動與 Collection 生命週期鏈路分析」第六、七、九、十節。以上轉述該文件的本機靜態分析與 Git 查核結果，未重新比對線上部署版本；提交紀錄能證明重建是刻意加入的行為，不能替代原始需求說明。

SMS 商品圈選：直接修改原 Collection

03 ／ SMS 商品圈選

同一份集合，更新裡面的商品

後台圈選商品時，畫面會帶著既有的集合 ID，把這次選取的商品送往後端。新增完成後，活動仍引用原本的集合，改變的是集合裡的商品內容。

本章放大給券活動 RewardReachPriceWithCoupon 的既有 fixed 商品集合新增路徑。以下鏈路依分析文件整理，成功情境以登入、活動與 API 驗證通過為前提。

起點：畫面必須已有集合 ID

給券 UI 的 onUpdate 先檢查 targetTypeCollectionId。已有 ID 才組成新增請求；尚無 ID 時，此回呼直接返回。

主鏈路：從圈選到原集合新增商品

SMS 後端轉換欄位後，呼叫 Promotion WebAPI 的 collection update。WebAPI 使用傳入的集合 ID 異動商品，再建立 PromotionTag 同步任務。

展開完整 API 路徑與內部責任
  • SMS 前端 Service 呼叫 Api/PromotionEngine/EditTargetIdList，進入 SMS PromotionEngineController.EditTargetIdList 與同名 Service 方法。
  • SMS PromotionEngineService.EditTargetIdList 驗證登入及活動，組成 CollectionUpdateRequestEntity。
  • SMS Nine1PromotionWebApiHttpClient.UpdateCollectionSalepages 發送 POST /api/salepage-collections/update。
  • Promotion WebAPI CollectionController.Update 依 IsRemoved 交給 CollectionService 的新增或移除方法。
  • CollectionHttpClientWithAudit 使用原 CollectionId 呼叫下游，異動商品並處理稽核。
  • CollectionService 建立 SyncCollectionToPromotionTagJob。時序圖中的自我呼叫是內部責任摘要，不表示同步任務已執行完成。
  • SMS 再取得商品數量，將處理結果與 TotalCount 回傳前端。

請求欄位：商品與操作方向如何傳遞

畫面傳入的是「這次要異動的商品」，後端將欄位轉成 WebAPI 的請求格式，並沿用既有集合 ID。

SMS 請求WebAPI 請求這條鏈路中的用途
IsRemoveIsRemovedfalse 是新增，true 是移除；本章已定位的 UI 回呼傳入 false。
RequestIdsSalePageIdList本次要新增或移除的商品 ID 清單。
既有集合 IDCollectionId指定要修改哪一份商品集合。
活動識別資料PromotionEngineId識別活動；與商品集合 ID 是不同用途。
商店資料ShopId指定此次操作的商店。
UI 的新增證據與 API 的增刪能力，需分開判讀。 分析文件定位到的給券 onUpdate 是新增方向。SMS 後端與 WebAPI 雖支援移除，仍不能推定所有給券 UI 移除操作都會即時走這條鏈路。

修改之後：ID 沿用，內容改變

假設活動 P 原本引用集合 A，內含商品 101、102；這次成功新增商品 103。

這條路徑不呼叫活動的 UpdateAsync，也沒有改走「重建 collection、重新產生活動 RuleRecord」的流程。稽核紀錄與 PromotionTag 同步任務，都不能視為活動整體更新。

第二章的歷史保留問題也因此成立：若舊規則引用同一個集合 ID，就需要進一步確認計算端如何讀取歷史商品範圍；僅憑本章鏈路，尚不能判定已造成錯算。

其他商品類型、補充欄位與查核邊界
  • SMS TargetType = Category 改走動態 collection；TargetType = MustSalePage 改走必購商品處理，均不屬於本章一般 fixed 商品集合主線。
  • WebAPI 的 IsRemoved = true 從原集合移除商品，false 在原集合新增商品，兩者皆沿用集合 ID。
  • TargetType、IsNeedRecordIo、UpdatedUser 等欄位供歷程處理；collection 的 UpdateIdx 是同一集合的異動版本，不等於更換 CollectionId。
  • 活動規則可保存帶前綴的集合識別值，呼叫下游前通常透過 GetCollectionIdWithoutPrefix() 去掉前綴，不能只按字串外觀判定是否換了集合。
  • API 驗證失敗時不進入後續核心更新。分析文件另指出，SMS Service 會將 collection 修改 API 的 400／500 回應轉成後台對應例外與訊息；本章時序圖未展開這些例外分支。
SMS 商品圈選的來源對照
  • 給券 UI：rewardCoupon.config.tsx:187，onUpdate 的既有集合判斷與新增請求。
  • SMS 前端：promotionEngine.service.ts:331，Api/PromotionEngine/EditTargetIdList。
  • SMS 後端：PromotionEngineController.cs:743 → PromotionEngineService.cs:3641 → Nine1PromotionWebApiHttpClient.cs:166。
  • Promotion WebAPI：CollectionController.cs:79 的增刪分流；CollectionService.cs:76 的原集合異動及同步任務。
